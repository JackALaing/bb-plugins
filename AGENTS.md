# BBPlugins

A pnpm workspace of BB plugins. One folder per plugin, `bb-plugin-<id>/`, each a normal BB plugin package (`package.json` carries the `bb` manifest). Use the `bb-plugin-authoring` skill for the Plugin SDK contract.

## Code here, run it from bb

Write all plugin code in this repo. Never edit a plugin inside `~/.bb/plugins/` — that directory holds BB's runtime state (`data.db`, logs, secrets), not source.

Link a plugin into bb by path, so bb loads this checkout in place:

```sh
bb plugin install ./bb-plugin-<id> --yes   # once per plugin
bb plugin dev ./bb-plugin-<id>             # rebuild + reload on every save
```

`bb plugin source <id>` should show a local path source pointing back here. If it does not, reinstall it from the path. Do not copy the folder into bb.

## Workspace

- Install with `pnpm install` at the root, never `npm install` in a plugin (no per-plugin `package-lock.json` or `node_modules`).
- `pnpm check` typechecks every plugin; `pnpm build` runs `bb plugin build` in each.
- New plugin: `bb plugin new <name>` in the root, delete its `node_modules` and `package-lock.json`, then `pnpm install`. Strip the todo demo.
- `bb plugin types ./bb-plugin-<id>` repins the SDK and shimmed packages when bb upgrades.
- Styling: do not use Tailwind utility classes. `bb plugin build` runs Tailwind over every file in the plugin folder (sources, README, docs, comments) and scopes each utility as `:where([data-bb-plugin="<id>"], [data-bb-plugin-root]:not([data-bb-plugin])) .flex`. BB's own elements carry the same class names, so the browser checks every plugin's copy of every rule on each style recalc: with 19 plugins this was ~200 of ~270ms of style work per thread switch (71ms with plugin CSS off). It also splits arbitrary values at their commas (`shadow-[0_8px_20px_-8px_rgba(0,0,0,.35)]` never applied). Write prefixed classes (`pinned-*`, `chat-dock-*`) in `src/styles.css` and import it from `app.tsx`: imported CSS is appended to `dist/app.css` unscoped and as written. Common words in prose (`flex`, `hidden`, `sticky`, `px-4`) still become scoped utilities, so check `dist/app.css` for `:where([data-bb-plugin=` after a build and reword the comment that made one.

## Plugins

- `bb-plugin-pinned-turns` — pins the user message you are reading under and the latest agent reply to the top of a thread's timeline; click either half to jump. Reference implementation: `dsh-chatux` (`src/model.ts`, `src/bands.ts`) — read it, never modify it.
  - `pnpm --filter bb-plugin-pinned-turns test` runs the model checks (`node --test`, no build). `bandAt` is checked against chatux's `bandContent` as an oracle.
  - Where it departs from chatux, on purpose: it searches row tops once (binary search) and reads titles from timeline data instead of reading every row's rect and text each frame; nothing polls on a timer except a 500ms check that the bar is still attached to BB's scroller (everything else is scroll + ResizeObserver); the pin line is the scroller's top edge, as in chatux (a lower line made the bar repeat a bubble still visible just under it). A jumped-to row lands `PIN_ROW_HEIGHT` (48px) below the edge, so the bar keeps naming what came before it.
  - Jumps steer by the row's live position each frame (close ~22% of the remaining distance, then hold ~20 frames to catch a late shift) instead of one `scrollTo`: BB mounts/unmounts and re-measures rows during a scroll, so a single smooth scroll stalled early or ended off by tens of px and then visibly corrected. A row that is windowed out is headed for 0.8 of a screen per frame, in the direction its rank says (read from where the mounted rows stand), which mounts the rows on the way. The page's URL and history are never touched (no `#msg=` jump): the back button must keep working as it did. Reader input (wheel/touch/pointer/key) cancels it; four frames where `scrollTop` cannot move (the first message sits under the bar and wants a negative offset) end it as `edge`.
  - Look follows chatux's README/`docs/features/IMPLEMENTED.md`: the bar hangs from the scroller's top edge (box lifted by its corner radius, 12px, with the top padding raised to match), the reply on the left takes the room the message leaves, the message on the right is shrink-to-fit up to 70% of the column, no labels, rise-on-hover shadow, blank halves fade out through the top.
  - Ink: BB's `--surface-recessed` is a translucent 6% tint, so a bar painted with it (or `hover:bg-surface-recessed`) lets the text underneath show through. Use `--surface-recessed-solid` (foreground 6% over background) for the message. The reply is the darker half in both themes via `light-dark()`: foreground 10% in light, 3% in dark (between the chat background and the bubble). BB follows `prefers-color-scheme` (html `color-scheme` flips), so a headless browser can check both with `page.emulateMediaFeatures([{ name: "prefers-color-scheme", value: "dark" }])` without touching the user's theme.
  - Width glide: the message half sizes itself to its text, so switching messages used to snap both halves. `useGlide` (`src/PinnedTurns.tsx`) animates that half's width from its previous (or in-flight) width to the new one over `GLIDE_MS` (100ms, ease-out) with the Web Animations API, in a layout effect so nothing paints at the new width first; the reply is `flex-1`, so it follows for free. Skipped under reduced motion and for first appearance; the settled width is tracked with a ResizeObserver so a window resize leaves no stale start.
  - Styling: no Tailwind utilities; the classes are the plugin's own (`pinned-*`) in `src/styles.css` (see Workspace). Gotchas: `text-overflow: ellipsis` does not work on a `<button>` itself, the text needs an inner `block truncate` span.
  - The thread-header pin button (`src/HeaderMenu.tsx`, `experimental_threadHeaderAction`) opens a Radix dropdown (`@radix-ui/react-dropdown-menu`, shimmed by BB, types only in devDependencies; portalled content spreads `usePortalScopeProps()` from `src/portal-scope.ts`) holding the on/off switch and the options. Each is a boolean plugin setting declared in `server.ts`: `enabled`, `showStatus` (a reply whose turn is running pulses its text; a dot marks failed/interrupted), `showPinButton` (hides the header button for good; the menu's "Show this button" switches it off and the plugin's page in BB settings, `/settings/plugins/pinned-turns`, switches it back on; the menu's "Plugin settings" row opens that page with `history.pushState` + a `popstate` event, since the SDK has no call for it and a link reloads the page), `showPosition` (on by default; "7/23", ordinal semibold, 90% size, 33% opacity, on the message text's baseline, hanging outside the message half's right edge so it never takes width; left out when the scroller is under `COUNTER_ROOM` 840px, where it would clip; counted from BB's conversation outline, `useOutline` in `src/timeline.ts`: one request of a few KB listing every user message by the timeline's row id, fetched after the first timeline page and again when the newest user message changes, so no older timeline pages are loaded for it), `showFullText` (native tooltip when the bar cut the text), `debugLog`. The frontend reads them with `useSettings()` (`src/options.ts`) but can only write through the backend (`set_setting` RPC → `settings.experimental_set`).
  - Options that cannot apply are greyed out in the menu with the reason in place of the hint (`src/viewport.ts`): the turn counter when the scroller is under `COUNTER_ROOM` (the bar reports its measured width through `setCounterRoom`, read in the menu with `useCounterRoom`; both are in one bundle so a module variable is the channel; the outline is not fetched for it either), and full text on hover when no pointer can hover (`(any-hover: hover)`, so touch-only devices; headless Chrome has no pointer and reports false). The tooltip is a native `title`, so it needs no code to be absent on touch.
  - Turn status (`turnStatus` in `src/model.ts`, fed by `indexOf` in `src/rows.ts`, which is pure and covered by `src/model.test.ts`): BB's error and interrupted system rows have `turnId: null`, so a turn is the rows between one user row and the next. Running (`status: "pending"` on any row) wins and is shown on both halves: the reply's text and the question's text pulse (the question matters when a turn has no reply yet); otherwise the last of reply / error / interrupted decides, so an error a later reply recovered from shows nothing.
  - Agent-initiated user rows (`initiator: "agent"`) are never named; system ones (`initiator: "system"`, child threads finishing) are, with the thread title, and read as "a system message". A user row with no text is titled from its attachments.
  - Debug log: off by default (switch it on in the menu), one line per event in the plugin log (`bb plugin logs pinned-turns`, level `debug`): `load`, `older`, `attach`/`detach`, `jump` (outcome settled/edge/cancelled/timeout/lost, ms), and a `timeline` summary every 5s of activity (`signals` vs `refetches`, `fetchMsMax`, `rows`). `signals` far above `refetches` with the reply title going stale would mean the 300ms debounce in `useTimeline` starves during streaming. Not seen so far (a streaming thread showed signals=13 refetches=4 over 7s); `fetchMsMax` reached ~1s on a 336-row active thread.
  - The RPCs are `set_setting` and `debug`. Timeline data needs no RPC: the page calls `useSdk().threads.timeline` (paged, newest first; `beforeAnchorId`/`beforeAnchorSeq` from `timelinePage.olderCursor`) and `sdk.subscribe({ event: "thread:changed", threadId })`. Older pages are fetched only when a half of the bar has nothing above it.
  - `useTimeline` (`src/timeline.ts`): signals refetch the newest page after 300ms of quiet or, in a stream that never pauses, 1s after the first one (`MAX_WAIT_MS`); changes that cannot alter a row (read state, title, pin, ...) are ignored; only the newest request's answer is used; a failed fetch retries after 3s; `history-rewritten`/`history-compacted` make the next fetch replace the held rows instead of merging; `olderRowUpdates` (rows older than the page that changed) are applied by id. The pure pieces (`flatten`, `mergeNewest`, `prependOlder`, `indexOf`) are in `src/rows.ts` and tested. A failing older-page fetch is not retried for 3s. The overlay waits for `useSettings().isLoading` to finish so a bar switched off does not flash on every thread. It also waits for the thread to settle (`useSettled` in `app.tsx`: two frames, then `requestIdleCallback` with a 1.5s cap) before mounting `PinnedTurns`, so its timeline fetch goes after BB's own and its setup after BB has drawn the rows. Measured over 6 switches: rows on screen 316–323ms without the plugin, 340ms mounting at once, 328ms delayed; the bar showed at ~520ms either way, since it waits for its data anyway.
  - Dev loop: `bb plugin dev` rebuilds in ~150ms and reloads the plugin in the open page without a navigation (state in `window` survives; the old bar is torn down, not duplicated).

- `bb-plugin-chat-dock` — moves BB's composer shell (`[data-app-composer]`: the cards above the box, the context row, the box, the chips under it) out of the chat column into the right panel while it is open. Nothing is re-implemented: the live element is moved with `moveInto` (`src/dom.ts`), which leaves a comment marker where it was and puts it back on undock, so the draft, the pickers' state and every plugin root inside it survive. Two modes, both plugin settings (`server.ts`, written through the `set_setting` RPC from the menu in `src/DockMenu.tsx`; the button, `src/DockButton.tsx`, is a composer action registered with `app.composer.customize({ scopes: ["thread"], actions })`, so it sits in the composer's action row and moves with the shell; BB hides composer actions in its compact one-line layout; its glyph is lucide's Dock, which BB's icon set lacks, registered by `app.experimental_icons.register` as `chat-dock/dock` from `src/icons.tsx`): `enabled` offers a fixed thread tab `chat` (`src/Dock.tsx`, `layout: "flush"`) that holds the shell while it is the active tab in its pane, since BB unmounts inactive tabs; `locked` (on by default) hides that tab and an app overlay (`src/Strip.tsx`, renders nothing through React) appends a host to the panel's flex column under the tab body, in flow so the open tab shrinks rather than being covered, once per `[data-split-resize-grid-root]` so split chat panes keep their own composer. Both undock while the panel is collapsed (`panelHidden`: `data-panel-size` 0 or `aria-hidden` on the aside, or `inert` on the phone-width drawer, watched with a MutationObserver) and re-dock on expand (`panelFor(root)` finds a pane's split panel or, failing that, the drawer; the drawer unmounts its aside while closed, so a missing aside is "no panel" and the shell goes home), and a 500ms check re-docks a shell BB rebuilt under the thread. A navigation to another thread with the panel open keeps the grid root, the panel and the aside (the column is replaced) and unmounts only the chat column, so React never removes a shell that was moved into a host: `moveInto`'s restore drops a shell whose home marker has no parent instead of leaving it, and the strip releases a held pane as "thread changed" and docks the new shell in the same pass when the pane's column offers a fresh `[data-scroll-footer] [data-app-composer]` (the tab re-runs its effect on the new `threadId` and goes through the same restore). The strip's `check` runs from one page-wide MutationObserver (`observePage`: childList in the whole subtree of `body` plus the `data-panel-size`/`aria-hidden`/`inert` attributes, with records whose target is inside `[data-timeline-items]` or `[data-app-composer]` ignored, so streaming rows cost nothing), so it lands in the same task as BB's DOM change, before a paint: a thread opened with the panel already open gets its shell docked in the frame the column mounts, never drawn in the column first (a 500ms timer remains as the backstop). Switching modes is one move, never a bounce through the column: BB remounts the aside's content after every plugin setting write (not on a tab switch), which detaches the strip's host with the shell inside, so the same observer runs `check` and `rehome` moves the host into the fresh column before a paint; during that remount the tab strip and body sit flat under the aside for ~100ms, so `findPanel` takes the column to be the lowest ancestor of `[data-testid=thread-secondary-panel-top-chrome]` that holds something else (the aside itself while flat) and `rehome` moves the host again once the column is back. A restored shell notifies `onShellHome` listeners (microtask) so the other dock takes it in the same task, and when the lock goes on while the tab holds the shell, the tab's root learns of it ~100ms before the overlay's, so the tab `park`s the shell in a strip host that the strip `adopt`s (a host not adopted within 1.5s restores itself). The menu stays open across its switches except the first, which closes it since the composer under it is about to move. The menu is rendered by a second app overlay, not by the button: a composer action is a React child of BB's composer, React replays a portal's events up through the owning tree, and the composer's capture-phase handlers took focus back (closing the menu before an item toggled) and expanded the box on every item click (a one-line grow for ~300ms). `src/menu-state.ts` is the channel (open flag and the button's rect; the overlay hangs a Radix menu from an inert fixed-position trigger at that rect; `onInteractOutside` ignores the button so its click toggles; `onCloseAutoFocus` is prevented since focus inside the composer expands it too). The button's own trusted `pointerdown` is stopped at the document in the capture phase (`installButtonGuard`) and its `mousedown` default is prevented, so opening the menu neither expands nor focuses the composer; the click still arrives. Headless checks need `page.mouse.click` on the button.

- `bb-plugin-stay-at-bottom` — a content script (`app.contentScripts.register`, `src/keeper.ts`) that keeps a thread scroller at its bottom. BB's scroll keeper takes a browser layout-pass clamp (the content is briefly shorter after the keeper's own write lands) for the reader scrolling: inside its 4px threshold the view creeps up a few px per row, past it the keeper detaches. The plugin keeps a per-scroller `pinned` flag (true when the view starts at the bottom, and again whenever a scroll ends there); while pinned, a `scroll` that leaves it above the bottom with no reader input in 500ms (wheel/keydown/pointerdown/touch, pointer not held, no touch in progress) is written back. A gap is repaired up to 96px normally (below one wheel notch), a full viewport when the content height or viewport width changed since the previous scroll (a growing row, the right panel opening), with a 24px floor for a tiny scroller; a larger gap or a larger move is navigation and turns `pinned` off. The repair is two frames: it lands 2px short of the bottom, then exactly on it. BB's keeper ignores scroll events within 0.5px of its own last write, so a single write back is invisible to it and leaves it detached — the "Scroll to latest event" arrow stays and the next row anchors; the second, downward 2px move re-attaches it. Pure pieces: `gapOf`, `repairCeiling`, `nextState` (the last two tested by `node --test src/keeper.test.ts`, run by the package `test` script). Scrollers are rescanned every 1s (navigation, split panes); every listener hangs off one AbortController so the disposer is one abort. The content script has no React, so the `enabled` setting reaches it through a module variable set by a null-rendering `experimental_appOverlay` (`src/Options.tsx`); the manifest requires `server.ts`, which only declares the setting. Headless check idiom: wrap `Element.prototype.scrollTop`'s setter to log writes with a stack and watch `[data-scroll-attached]` (the marker BB puts on an inner wrapper, not the scroller's first child) plus the footer `button[aria-label="Scroll to latest event"]`; a 3px or 80px synthetic dip must end at gap 0 with the marker present and the button hidden, 250px without a layout change must stay (as must 400px), a `wheel` event (or 300px position held after one) plus content growth must stay, and opening/closing the right panel at the bottom must leave gap 0 and the marker. `bb plugin config <id> set enabled false` gives a control run (the content script keeps listening but does nothing); check the setting again after a reload. `bb plugin reload` disposes the old mount.

## BB timeline DOM facts (bb-app 0.47.0, undocumented, can change)

- Scroller: `[data-page-scroll-viewport]` (overflow-y auto, `overflow-anchor: none`). The 48px `<header>` is outside it, so the scroller's top is already below the header. The thread TOC (`[data-thread-toc]`, ~32px wide, right edge ~12px in) is an overlay sibling at z-30, not inside the scroller, and sits at the vertical middle of the right edge, so it does not meet a bar at the top. The bar uses the text column's own 16px side padding (`px-4`, max 728px) so it lines up with the text at every width.
- Rows: `[data-timeline-row-id]` inside `[data-timeline-items]`. There is no `data-index`; use DOM order. Conversation row ids equal the timeline data's row ids (`thr:user-seed:<seq>`, `thr:assistant:kind:assistant|…`), so data and DOM join on id. BB folds runs of work rows into `<thr>:<turn>:work-summary:<data id of a member>`, which has no data row of its own.
- A user-role row is not always something the user typed: child-thread completions are `[bb system] @thread:…` user rows (`initiator: "system"`) and draw as the thread title. Use `mentions` (`start`, `end`, `resource.label`) to title them.
- User rows: row id `<threadId>:user-seed:<seq>`, and `<seq>` is the event sequence that `#msg=<seq>` takes (the plugin does not use it). `[data-message-column]` is on assistant rows too, so do not use it to spot user messages. Assistant rows: `…:assistant:kind:assistant|turn:<t>|parent:…|item:<i>` (no seq).
- Virtualization: on when the top-level row count is ≥ 20. Unmounted ranges are `div[data-timeline-window-spacer][aria-hidden]` with a pixel height, interleaved with the mounted rows, so `scrollHeight` shifts as rows are measured. The last row is always mounted.
- Jump: setting `location.hash = "#msg=<seq>"` on the open thread scrolls in place and mounts the row, landing it 16px below the scroller top, but pushes a history entry, so the plugin does not use it; it scrolls the scroller itself.
- The URL is `/projects/<projectId>/threads/<threadId>`; never build thread URLs by hand.

## BB thread page DOM facts (bb-app 0.47.1, undocumented, can change)

- A thread page is one `[data-split-resize-grid-root]` per chat pane holding `#thread-detail-timeline-panel` (the chat column) and `#thread-detail-secondary-panel` (the right panel), each `[data-panel]` with `data-panel-size` (percent; the right panel is 0 when hidden, 100 when maximized). The right panel's `aside` gets `aria-hidden="true"` and `inert` when hidden; its one child is a flex column: the tab strip (`[data-testid=thread-secondary-panel-top-chrome]`, `[data-tab-pill]`s, `[data-panel-new-tab]`, "Maximize pane"/"Restore split", "Hide right panel (Ctrl + J)") then the tab body (`flex-1 min-h-0`), where a plugin tab renders inside `[data-bb-plugin-root][data-bb-plugin=<id>]`. Tab splits are persisted under `localStorage` keys prefixed `bb-secondary-panel-split`.
- The chat column's scroller frame ends in `[data-scroll-footer]` (`sticky bottom-0`), rendered only when the thread view supplies a footer; it holds a zero-height row with the "Scroll to latest event" button and the composer shell `[data-app-composer][data-app-composer-role=primary][data-promptbox-shell]`. The shell is a grid of plugin roots (breathe, composer-predictions, scheduled-send, workflows), `section[aria-label="Thread context before sending"]` (changed files, merge base; the `experimental_threadContextSegment` slot), the running-command / child-thread / question cards when there are any, then `[data-follow-up-composer-anchor] > [data-follow-up-composer]` with `[data-composer-box]` (the bundled `bb--composer` plugin's tiptap editor, `[data-promptbox-editor-content] [contenteditable]`) and `[data-follow-up-composer-footer]` (project, environment, branch, permission mode, cost chips). The turns are a sibling of the footer.
- The scroll body (`bottom-anchored-scroll-body-*.js`) keeps a ref to the footer for its bottom-anchoring and `scroll-padding-bottom`; moving the shell out leaves a 16px footer behind and nothing breaks. The composer's compact one-line form is a container query, `@container promptbox-shell (width <= 30rem)` sets `--follow-up-composer-container-compact: true` on `[data-follow-up-composer]`, so it follows the shell wherever it is.
- No SDK API reads or sets the right panel's open state, split layout or active tab; `experimental_tab` components mount only while active, `experimental_appOverlay` is the one plugin surface mounted regardless.
- Under a phone-width viewport (390px tested) there is no `#thread-detail-secondary-panel`: the grid holds only the chat column, which slides off-screen (x = -width) when the panel opens, and the panel is `div[data-testid=secondary-panel-shelf]` (`role=dialog`, fixed, full width, a child of `body`), inert while closed with its aside unmounted; open, it holds `div > aside` with the same tab strip and body as the split panel. BB hides composer actions in this compact layout, so the dock button is absent there and the settings are reached through the plugin's settings page.
- An in-app navigation between threads (the router, not a reload) keeps `[data-split-resize-grid-root]`, `#thread-detail-secondary-panel` and its `aside` as the same elements and replaces the aside's column and the chat column; the right panel's open state is per thread (a thread where it was never opened shows it collapsed).
- Every plugin setting write (`settings.experimental_set`) makes BB remount the right panel's content: the aside's column is replaced, with a ~100ms flat state in between where the tab strip and the body are direct children of the aside. Anything a plugin appended to the column is detached. A tab switch does not do this.
- `experimental_Icon` names are BB's own set (~180 names in the app bundle: `AlertCircle`…`Zap`, plus the lazy `icon-extended` chunk with `PanelRight`, `PanelBottom`, `SideChat`, `Pin`, `MoveTo`, `Columns2`, `Rows2`, `Layers`, `ListEnd`, `TextWrap`, `SectionMove`…), not lucide: a lucide name BB lacks (`PanelRightDashed`, `Dock`) renders the `fallback`. A plugin can ship its own glyphs through `bb.branding.experimental_icons` or `app.experimental_icons.register()`.
